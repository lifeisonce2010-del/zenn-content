## 有志製ツールを使うということ

本書で使っているMCPサーバーは、Adobe公式のものではありません。有志が作ったオープンソースです。

つまり、**バグが残っていることがあります。**

これは欠点のように聞こえますが、実は大きな利点でもあります。ソースコードが手元にあるので、壊れていたら直せるのです。しかも、直すのはあなたではなく、AIです。

この章では、私が実際に遭遇したバグを、AIと一緒に特定して修正した全記録を載せます。同じバグに当たるかは分かりませんが、**「ツールが壊れている疑いを持ち、自分で切り分けて直す」という手順**は、そのまま使えます。

## 発端：数字がおかしい

タイムラインのクリップ一覧を読み取ったところ、こう返ってきました。

```
全クリップ enabled: false（=無効化）
V1 上の 12 クリップは全部ミュート状態です。
```

ここでAIが良い仕事をしました。**勝手に直さず、確認を求めてきた**のです。

```
作業中の意図的な非表示か、レンダーミスかは判断つかないので、
変更前に一声かけてください
```

そこで「全部有効に戻して」と指示したところ、今度はこうなりました。

```
12件すべて EvalScript error で失敗しました。
```

読み取りは成功するのに、書き込みが全部失敗する。ここで「ツール側を疑う」という発想が出てくるかどうかが分かれ目です。

## AIの切り分けプロセス

AIは次の順で原因を追い込んでいきました。この思考の流れ自体が学びになります。

**1. 並列実行を疑う**

> ExtendScript は同時実行に弱いので、並列で叩いたのが原因かもしれません。逐次で再試行します。

→ 逐次でも失敗。

**2. ツールの呼び出し方を変える**

> `enable_disable_clip` は単体呼び出しでも失敗するので、このツール自体の不具合っぽいです。`execute_extendscript` で直接プロパティを書き換える方法にフォールバックします。

→ ここで**想定外の結果**が出ます。

**3. 前提が崩れる**

> ExtendScript から直接プロパティを読むと、12クリップ全部が最初から `disabled: false`（=有効）でした。

つまり、**最初の読み取り結果が間違っていた**のです。クリップは無効化などされていませんでした。

**4. ソースコードを読みに行く**

> MCP の `get_timeline_clips` の `enabled` フィールドの実装がバグっているかもしれません。念のためリポジトリ側の実装を確認します。

## 見つかったバグ2件

`cep/jsx/timeline.jsx` に、2つの誤りがありました。

### バグ1：読み取りが「選択状態」を返していた

```diff
- enabled: clip.isSelected(),
+ enabled: !clip.disabled,
```

`isSelected()` は「そのクリップが選択されているか」を返します。有効/無効とは無関係です。クリップを選択していなかったので、全部 `false` になっていた——それだけでした。

**数字が全部同じ値のときは、実装を疑う価値があります。**

### バグ2：存在しないメソッドを呼んでいた

```diff
- clip.setDisabled(!enabled);
+ clip.disabled = !enabled;
```

Premiere Pro の `TrackItem` オブジェクトに `setDisabled()` というメソッドは存在しません。正しくはプロパティへの代入です。

存在しないメソッドを呼んだので、ExtendScript が例外を投げ、それが `EvalScript error` として返ってきていたわけです。**この機能は、最初から一度も動いたことがなかった**ことになります。

## 修正を反映させるまでの罠

2行直せば終わり……とはいきませんでした。ここからが本番です。

### 罠1：.jsx はキャッシュされる

ファイルを直しても、Premiere 側の ExtendScript エンジンには古いコードがメモリに残ったままです。

パネルを閉じて開き直す（ウィンドウ → 機能拡張 → チェックを外す → 入れ直す）のが基本の対処です。

### 罠2：ファイルは新しいのに、動くコードは古い

パネルを再読み込みしても、まだ古い結果が返ってきました。AIはここで、インストール先とリポジトリの両方を比較しにいきます。

```
2つのディレクトリは中身もタイムスタンプも完全に同じ
（=Windows junction で symlink されている）
ファイルは NEW コードだが、メモリ上の関数は OLD という奇妙な状態
```

**ファイルの二重管理は不要**だと分かったのは収穫でした。インストール先の `com.mcp.premiere.bridge` は、リポジトリの `cep/` への junction（Windowsのシンボリックリンク）なので、リポジトリを直せば両方に反映されます。

### 罠3：スコープの問題

では、なぜメモリ上の関数が古いままだったのか。

```
$.evalFile() を IIFE の内側 で呼んでいたので、
再定義されたはずの関数が IIFE のローカルスコープに閉じ込められ、
グローバルには反映されていませんでした。
```

JavaScriptの関数宣言は、その時点のスコープの先頭に巻き上げられます。IIFE（即時実行関数）の中で `$.evalFile()` を呼ぶと、読み込まれた関数定義はそのIIFEの中だけのものになり、外側からは見えません。

**グローバルスコープで `$.evalFile("<絶対パス>")` を実行する**——これが正解でした。

:::message
この3つの罠は、`.jsx` を自分で書き換えるときは必ず通る道です。「直したのに反映されない」と思ったら、ファイル・メモリ・スコープの3段階を疑ってください。
:::

## 検証結果

最終的に、次の5ステップで両方の修正を確認しました。

| 手順 | 期待 | 結果 |
| --- | --- | --- |
| `get_timeline_clips`（初期） | 全12個 `enabled: true` | ✅ |
| `enable_disable_clip(clip=0, false)` | EvalScript error にならず成功 | ✅ `{ enabled: false, success: true }` |
| `get_timeline_clips`（無効化後） | クリップ0のみ `enabled: false` | ✅ |
| `enable_disable_clip(clip=0, true)` | 復元成功 | ✅ `{ enabled: true, success: true }` |
| `get_timeline_clips`（復元後） | 全12個 `enabled: true` | ✅ |

**書き込み → 読み取りで確認 → 元に戻す。** この型で検証すると、プロジェクトを汚さずに機能テストができます。

## 3件目：「成功しました」と言うのに、切れていない

`enabled` の2件を直したあと、本題のカット編集を頼みました。

```
V1の10番目のクリップ（10_lineup.png、25.526秒〜29.029秒）を、
27.0秒の位置で2つに分割して
```

返ってきたのは `{"success": true}`。ところが、クリップを読み直すと12個のまま。**何も切れていません。**

ここでもAIは、「成功」という返事をうのみにせず、読み直して確かめました。

```
razor_clip は success: true を返したものの、実際には分割されていません
（クリップ数 12 のまま、10_lineup.png の尺も 3.5035 で変化なし）。
もう1件バグの匂いです。実装を見ます。
```

### 原因：渡す値の形式が違っていた

実装は、秒数を「ticks」という内部単位の数値に変換して渡していました。

```js
qeTrack.razor(_makeTime(timeSec).ticks);
```

AIは、渡し方を3通り試して比べました。

| 渡した値 | 例外 | クリップ数 |
| --- | --- | --- |
| ticks（数値）`6858432000000` | 出ない | 12 → 12（変化なし） |
| ticks（文字列）`"6858432000000"` | 出ない | 12 → 12（変化なし） |
| タイムコード `"00;00;27;00"` | 出ない | 12 → **13（成功）** |

分割の命令は**タイムコードの文字列しか受け付けず、それ以外は例外も出さずに無視する**、という作りでした。

修正では、シーケンスの設定からタイムコードを作って渡します。

```diff
+  var seq = app.project.activeSequence;
+  var s = seq.getSettings();
+  var tc = _makeTime(timeSec).getFormatted(s.videoFrameRate, s.videoDisplayFormat);
   app.enableQE();
   ...
-  qeTrack.razor(_makeTime(timeSec).ticks);
+  qeTrack.razor(tc);
```

フレームレートを決め打ちしていないので、24fpsでも60fpsでも同じように動きます。修正後に14.0秒で分割を指示すると、29.97fpsのフレーム境界（13.981秒）でちゃんと切れました。

:::message alert
**`success: true` は「命令を送れた」という意味でしかないことがあります。** 書き込み系の操作のあとは、必ず読み直して結果を確かめてください。AIに頼むときは「完了したら読み取って報告して」と付けるだけで十分です。
:::

## 4件目：「元に戻す」が何もしない

分割の動作確認で入れた余分なカットを消そうと、`undo` を頼みました。返事はまた `{"success": true}`。でもカットは残ったままです。

```js
function undo() {
  app.enableQE();
  try { qe.project.undoStackManager.undo(); } catch (ex) {}
  return _ok();
}
```

`undoStackManager` は今のPremiereには**存在しません**。存在しないものを呼んだときのエラーを `catch (ex) {}` で握りつぶしたうえで、無条件に「成功」を返していました。

### ここで一度、AIも私も間違えた

最初の調査では、`qe.project` が持っている項目を一覧で出しました。

```
currentRendererName, importFailures, isAudioConforming, ..., numSequences, path
```

undo に関係しそうな項目は一つもありません。そこで「ExtendScriptから元に戻すAPIは無い」と結論し、Ctrl+Zを手で押してもらいました。

**この結論は誤りでした。** 後日、一覧に頼らず名前を指定して直接確かめると、こうなりました。

```
typeof qe.project.undoStackManager → "undefined"
typeof qe.project.undo             → "function"
typeof qe.project.redo             → "function"
```

`undo` は存在していました。**一覧に出てこないだけ**だったのです。Premiereの内部オブジェクトには、一覧（`for...in`）には現れないメソッドがあります。

:::message
「一覧に無い＝存在しない」ではありません。存在を確かめるときは `typeof 対象.名前` で直接聞いてください。
:::

### 修正

```diff
 function undo() {
   app.enableQE();
-  try { qe.project.undoStackManager.undo(); } catch (ex) {}
-  return _ok();
+  if (typeof qe.project.undo !== "function") {
+    return _err("Undo API not available in this Premiere version");
+  }
+  try {
+    qe.project.undo();
+  } catch (ex) {
+    return _err("Undo failed: " + ex.toString());
+  }
+  return _ok();
 }
```

直したのは3点です。

1. 存在しない `undoStackManager` ではなく `qe.project.undo()` を呼ぶ
2. APIが無ければ、はっきり「使えない」と返す
3. 例外を握りつぶさない

### 直ったか確かめる

分割 → 元に戻す → やり直し → 元に戻す、の順に実行し、そのたびにクリップ数を読み直しました。

| 手順 | 返事 | クリップ数（読み直し） |
| --- | --- | --- |
| 14秒で分割 | success | 10 → 11 ✅ |
| `undo` | success | 11 → 10 ✅ |
| `redo` | success | 10 → 11 ✅ |
| `undo` | success | 11 → 10 ✅ |

修正前は「success」と返しながら何も起きていませんでした。**返事と実際の状態が一致して、初めて「直った」と言えます。**

## 5件目（ツールではなく、検証のやり方のバグ）：別のプロジェクトを触っていた

これはツールのバグではなく、**検証する側の落とし穴**です。いちばん危なかったので載せておきます。

### 検証用に保存したはずのファイルに、シーケンスが無い

検証の最初に、プロジェクトを `mcp-test.prproj` という名前で保存し直しました。以降はずっとそのファイルで作業しているつもりでした。

後日そのファイルを開くと、**シーケンスが1つもありません。** 12枚のPNGが並んだ `PR_9x16` シーケンスは、まったく別の、**実際の案件のプロジェクト**に属していました。

Premiereは複数のプロジェクトを同時に開けます。あのとき「アクティブなシーケンス」は実案件側のものでした。そのため `get_project_info` が「シーケンス数 0」と返しているのに、タイムラインの操作は実案件のシーケンスに効いていたのです。導入編の記事で「`numSequences: 0` なのにシーケンスがある食い違い」と書いた現象の正体は、これでした。

幸い、実案件は保存していなかったので、ファイルは無傷でした。

### 再発：チュートリアルに切れ目を入れた

対策として、実案件のコピーを作り、それを開いて検証を再開しました。ところが、Premiereを再起動すると、学習パネルのチュートリアル用プロジェクトも裏で一緒に開いていました。

`get_project_info` は「コピーを開いています」と答えます。一方で、スクリプト内の `app.project` はチュートリアルを指していました。結果、**検証の分割がチュートリアルに入りました。**

:::message alert
書き込む前には、**同じスクリプトの中で** `app.project.path` を確認してください。ツールを呼ぶたびに「今どのプロジェクトを触っているか」は変わりえます。前のツールの返事を信用しないこと。
:::

AIに頼むときは、次のように書き添えると安全です。

```
操作の前に、今どのプロジェクトのどのシーケンスが対象かを読み取って報告して。
検証用のコピー以外だったら、何も変更せずに止まって
```

## 残りのツールも総点検したら、さらに5件

ここまでで「成功と言って何もしない」パターンが見えてきました。そこで、同じ仕組み（QE API）を使っているツールを、1つずつ実機で叩いて読み直しました。

| ツール | 何が起きたか |
| --- | --- |
| `ripple_delete` | 「成功」と返すが、何も消えない |
| `slip_clip` | 「成功」と返すが、何も変わらない |
| `slide_clip` | 「成功」と返して、**クリップを約10時間後に吹き飛ばした** |
| `nest_clips` | 中身が未実装なのに「成功」と返す |
| `apply_transition` | 実在する名前を渡しても「見つからない」 |

### いちばん怖かった `slide_clip`

0.1秒だけ右にずらすよう頼みました。返事は `success: true`。読み直すと、こうなっていました。

| クリップ | 前 | 後 |
| --- | --- | --- |
| A011 | 7.716秒〜8.884秒 | **36043.716秒〜**（約10時間後） |
| 隣のクリップ | 〜7.716秒で終わる | 〜**36043.716秒**まで伸びた |

0.1秒のはずが、約36036秒としてずらされていました。**「成功」と言いながら作品を壊す**。今回見つけたなかで最悪のバグです。

幸い、直したばかりの `undo` が1回で完全に元に戻してくれました。前の節で `undo` を直していなければ、手で直すしかなかったところです。

:::message alert
スリップ・スライド・リップル削除のように「タイムライン上の時間を動かす」ツールは、**必ず複製したプロジェクトで試してから**使ってください。実行前に `save_project_as` で退避しておくのも有効です。
:::

### 共通の原因1：QEは「空白」も1個に数える

`ripple_delete` が効かなかった理由を調べると、もう1つ根深い問題が見つかりました。

Premiereの内部API（QE）でトラックの中身を並べると、**クリップとクリップの間の空白も1つの項目**として数えられていました。

```
標準API:  [クリップ0] [クリップ1] [クリップ2] ...          → 10個
QE     :  [クリップ0] [空白] [クリップ1] [クリップ2] ...  → 12個
```

MCPのツールは「何番目のクリップ」を標準APIの番号で受け取ります。ところが実際の操作はQEの番号で行っていました。**最初の空白より後ろのクリップは、1つ手前のクリップを操作してしまう**わけです。この取り違えは9か所にありました。

### 共通の原因2：一覧が「文字列の配列」だった

トランジションやエフェクトの一覧は、名前（`.name`）を持つオブジェクトの集まりとして扱われていました。実際には**ただの文字列の配列**です。そのため、一覧を返すツールは常に空（`[]`）を返し、名前でトランジションを探す処理は必ず失敗していました。

日本語版のPremiereでは、名前も日本語です（`クロスディゾルブ`、`暗転` など）。ツールの説明にある `'Cross Dissolve'` という例は、日本語環境では当たりません。

## 一般化：あなたが同じ状況になったら

### ツールを疑うべきサイン

- 全件が同じ値を返す（`false` が12個並ぶ、など）
- 読み取りは成功するのに書き込みだけ全部失敗する
- 画面上の見た目とAIの報告が食い違う
- エラーメッセージが `EvalScript error` のように具体性を欠く
- `success: true` なのに、読み直すと何も変わっていない
- プロジェクト情報とタイムラインの状態が食い違う（シーケンス数0なのにシーケンスがある、など）

### AIへの頼み方

そのまま使える指示文です。

```
この機能が動かない。MCPサーバーのソースを読んで、
実装にバグがないか確認して。
原因が分かったら、修正案をdiffで見せて。
まだ修正は適用しないで
```

「まだ適用しないで」を付けるのが大事です。**原因の説明を読んでから、直すかどうかを自分で決められます。**

### 直したあとの選択肢

1. **手元に置いておく** — 一番手軽。ただしツールを更新すると消える
2. **fork して自分のリポジトリに持つ** — 更新に追従しつつ修正を維持できる
3. **本家にPull Requestを出す** — 他の人も救われる。OSSへの貢献になる

どれを選んでも構いませんが、**最低限「何をどう直したか」はメモに残してください。** 半年後の自分が必ず忘れます。

## この章のまとめ

- 有志製ツールにはバグが残っていることがある
- ソースが手元にあるので、AIに読ませて直せる
- 「全件同じ値」「書き込みだけ失敗」はツールを疑うサイン
- `.jsx` の修正は、ファイル・メモリ・スコープの3段階で反映を確認する
- 検証は「**対象を確認** → 書き込み → 読み取りで確認 → 元に戻す」の型で
- `success: true` を信じない。書き込んだら必ず読み直す
- QEは「空白」も1項目に数え、一覧は文字列の配列。番号と名前の扱いに注意
- 時間を動かすツール（スリップ・スライド・リップル削除）は、複製したプロジェクトで試す

ツールが壊れていても詰まない。**これがオープンソースを使う一番の利点です。**
